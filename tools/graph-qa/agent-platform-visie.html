De agent als centraal platform

De huidige situatie bestaat uit losse onderdelen: een webapp voor analyses, een chatbot voor vragen, een kennisgraaf als databron. De volgende stap is één centrale agent die al deze functies integreert, orkestreert en de kennisgraaf actief verrijkt.

Huidige situatie

Analyses via webapp/skill, chatbot als bijzaak, kennisgraaf alleen voor lezen. Geen terugkoppeling.

Transitie

Agent krijgt een wetsanalyse-specialist. Analyses worden geannoteerd teruggeschreven naar de graaf.

Eindsituatie

Agent is het platform: analyseert, annoteert, formaliseert en beantwoordt vragen vanuit een rijke, levende kennisgraaf.

Huidige situatie

Wat er nu is — en wat ontbreekt

Losse onderdelen

  • Wetsanalyse-skill (Claude Code) — interactief, voor analisten
  • Webapp + API — zelfstandige dienst voor niet-technische gebruikers
  • Kennisgraaf (GraphDB) — wettekst als RDF, read-only
  • Chatbot Lex — beantwoordt vragen, als bijzaak in de webapp
  • RegelSpraak-export — vervolgstap na analyse

Wat ontbreekt

  • Analyses schrijven niets terug naar de kennisgraaf
  • De graaf wordt niet rijker van elke uitgevoerde analyse
  • De chatbot kan niet redeneren over JAS-annotaties
  • Geen gedeelde intelligentie tussen de onderdelen
→

Met de agent centraal

  • Agent voert wetsanalyses uit (nieuwe specialist)
  • Goedgekeurde annotaties worden teruggeschreven naar de graaf
  • De graaf groeit na elke analyse — rijkere retrieval
  • Chatbot Lex profiteert direct van elke nieuwe annotatie
  • Decompositie × annotaties = preciezere, betrouwbaardere antwoorden
  • Batch-worker: agent verwerkt de hele wet automatisch

De vliegwielwerking

Meer analyses → rijkere graaf → betere antwoorden → vertrouwen in het systeem → meer gebruik → meer analyses.

De graph-qa agent is operationeel op https://graph-qa.ipalm.nl. Hij heeft een volledig LangGraph-orkestrator, drie specialisten, een getypeerde toollaag en SSE-streaming. Dit is het fundament waarop de uitbreiding wordt gebouwd.

Algemeen
Brede vragen over wetgeving en juridische context.

Controleert elk antwoord op brongetrouwheid voor verzending.

  • Bearer-token authenticatie
  • SSE-streaming naar de webapp

  • Conversation-id per sessie of batch-job
  • Geïsoleerd per context (chat vs. batch)
Uitbreiding stap 1

Vierde specialist — Wetsanalyse

De agent krijgt een vierde specialist: Wetsanalyse. Die voert activiteit 2 en 3 uit conform de JAS-methode — dezelfde logica als de bestaande skill/API, maar nu ingebakken in de agent. De analist vraagt: "annoteer artikel 9 lid 1 Invorderingswet" — de agent doet de rest.

Wat de specialist doet

  • Wettekst ophalen via Wettenbank-MCP
  • Verwijzingen inventariseren en volgen (diepte 1)
  • Activiteit 2 — markeren in 13 JAS-klassen
  • Activiteit 3a — begrippen opstellen
  • Activiteit 3b — afleidingsregels annoteren
  • save_annotatie aanroepen na akkoord

Minimale codewijzigingen

  • Één nieuw specialist-bestand in agent/specialists.py
  • annotatie_graph-config in agent/config.py
  • batch_mode-vlag in de LangGraph-State
  • save_result-event voor worker-signalering
  • JAS-klassen als constante in prompts.py
  • Router overgeslagen bij bekende specialist

Akkoord-stap blijft verplicht

In interactieve modus vraagt de specialist bevestiging van de analist vóór opslaan. In batch_mode slaat hij op naar de staging-named-graph — een menselijke reviewer accordeert daarna via de CLI-reviewer vóór promotie naar productie.

Annotaties terugschrijven naar de kennisgraaf

Twee named graphs

  • Ruwe LLM-annotaties, onzichtbaar voor de chat-agent
  • Productie — https://ipalm.nl/analyse/
  • Alleen goedgekeurde annotaties, zichtbaar voor chat

GraphWriter — veiligheidslaag

  • Accepteert alleen insert_annotatie-patronen
  • Geen vrije SPARQL-updates mogelijk
  • Schrijft via GraphDB SPARQL Update HTTP-endpoint
  • MCP-client blijft read-only (_reject_updates)

JAS-annotatie in de graaf

Elke annotatie volgt een vast IRI-patroon en koppelt aan de bestaande wettekst-nodes:

  • jas:Markering — klasse, citaat, vindplaats
  • jas:Begrip — definitie, relaties, herkomst
  • jas:Afleidingsregel — type, begrip-koppelingen
  • jas:bronBepaling → koppeling naar bwb:Lid
  • jas:bronReferentie — jci-uri (exact artikel + lid)
  • jas:goedgekeurdDoor / jas:tijdstip — auditspoor

De agent als batch-processor

De queue-worker is een dunne schil bovenop de bestaande answer_stream(). Hij roept de agent aan met een vaste wetsanalyse-prompt per queue-item — geen eigen LLM-logica, geen eigen MCP-client. De agent-laag wordt 100% hergebruikt.

Queue-item

  • bwb_id, artikel, lid
  • Status: pending → running → staged → akkoord
  • SELECT FOR UPDATE SKIP LOCKED — geen dubbel werk

Batch-mode

  • batch_mode: True in LangGraph State
  • Router overgeslagen, direct naar wetsanalyse-specialist
  • Staging-IRI via Settings.annotatie_graph
  • Unieke conversation_id per queue-item

Doorput

  • 3 gelijktijdige workers (Synology-safe)
  • ~10–15 artikelen per uur (LLM-afhankelijk)
  • Invorderingswet (~140 art.) ≈ 10–15 uur
  • Gefaalde items → status fout, handmatig retry
Synergie

Decompositie × annotaties — hoe ze elkaar versterken

Zonder annotaties

De decompose-node splitst een complexe vraag in deelvragen. Elke deelvraag leidt tot full-text retrieval — de LLM leest en interpreteert wettekst.

  • Deelvraag → full-text search → tekstfragment → LLM leest
  • Fout in één deelvraag contamineert het eindantwoord
  • Drie deelvragen nodig voor één multi-hop vraag

Met annotaties

De decompose-node kan deelvragen formuleren die direct op de annotatie-laag landen — deterministisch, zonder LLM-interpretatie.

  • Deelvraag → SPARQL op jas:Klasse → exacte treffer
  • Multi-hop in één SPARQL-query (rechtsbetrekking → verwijzing → doelregeling)
  • Synthesize-node combineert betrouwbare bouwstenen, geen gissingen

Wat decompositie blijft oplossen

Drie dingen blijven buiten de annotatie-laag: temporele redenering (vergelijken van wetsversies), casuïstiek (subsumptie: past situatie X onder artikel Y?), en onbekende scope (brede zoekslag vóór gerichte verdieping). Decompositie structureert die stappen — de annotatie-laag maakt de verdiepingsstap scherper.

De echte synergie

De decompose-node kiest bewust welke deelvragen via SPARQL op annotaties gaan en welke via tekst-retrieval — en geeft die keuze mee in de subagent-prompt. Niet minder decompositie — slimmere decompositie.

Groeiende kennisgraaf

Wat er mogelijk is als de graaf geannoteerd is

Rijkere retrieval nu

  • SPARQL op JAS-klasse i.p.v. full-text zoeken
  • "Geef alle Rechtssubjecten in de Invorderingswet" — één query
  • Multi-hop: rechtsbetrekking → verwijzing → definitieartikel
  • Deelvragen van decompose-node landen direct op annotaties

Consistentiecontrole

  • Detecteer conflicterende definities van hetzelfde begrip
  • Vind artikelen met overlappende Rechtssubjecten
  • Signaleer ontbrekende Brondefinities voor gebruikte termen
  • Audit: welke afleidingsregels missen een Voorwaarde?

Impact-analyse

  • Welke begrippen worden geraakt door wetswijziging X?
  • Welke afleidingsregels bouwen op parameter Y?
  • Transitieve impact-graaf over de hele wet

RegelSpraak zonder ruis

  • SPARQL CONSTRUCT genereert RegelSpraak-skelet direct
  • LLM vult alleen de taalkundige formulering in
  • Minder hallucinaties — structuur staat al vast in de graaf

De redenerende kennisgraaf

Als de hele Invorderingswet geannoteerd is, is het systeem geen zoekmachine meer maar een redenerende kennisgraaf: regeldetectie zonder LLM-redeneerslag, volledige impact-analyse, automatische consistentiecontrole. De agent beantwoordt vragen die vandaag onmogelijk zijn.

Kwaliteit

Drie lagen van kwaliteitsbewaking

Mechanische validatie
validate_annotatie.py — geldige JAS-klassen, aanwezige bronreferentie, letterlijk citaat. Blokkeert bij fouten.
Staging-isolatie
Batch-output gaat altijd naar staging-named-graph. Chat-agent ziet staging niet. Geen contaminatie.
Menselijke review
review_staged.py toont per artikel de annotaties. Analist: akkoord → promotie naar productie, of afwijzen → retry.

CLI-reviewer (review_staged.py)

  • Toont per queue-item: artikel, markeringen, begrippen, regels
  • Vorige versie ernaast (als het een herwerking is)
  • Keuze: akkoord → productie / afwijzen → terug naar pending
  • Reviewhistorie vastgelegd in queue-tabel (akkoord-tabel)

Promotie-query

  • Kopieert van staging naar productie via SPARQL UPDATE
  • Verwijdert de staging-triples na promotie
  • Voegt jas:goedgekeurdDoor en tijdstip toe
  • Atomair — geen gedeeltelijke promoties mogelijk

Conclusie

Van losse onderdelen naar één platform

De agent hergebruikt alles

De wetsanalyse-specialist, de batch-worker en de verbeterde chatbot bouwen op answer_stream(). Geen duplicatie van LLM-logica, geen aparte pipelines. De agent-laag is het gedeelde fundament.

De graaf wordt slimmer

Elke goedgekeurde analyse voegt JAS-annotaties toe aan de kennisgraaf. De chatbot profiteert direct. Het systeem leert cumulatief — niet door fine-tuning maar door groeiende, gevalideerde kennis.

De analist blijft centraal

De kwaliteitspoort is menselijk. Staging-isolatie, mechanische validatie en de CLI-reviewer garanderen dat alleen gevalideerde kennis de productie-graaf bereikt. De agent is het gereedschap, de analist de autoriteit.

Schaalbaar zonder herschrijven

Fase 1 en 2 vereisen minimale codewijzigingen in de bestaande agent. Elke fase levert direct waarde. Het platform groeit incrementeel terwijl het vandaag al operationeel is.
